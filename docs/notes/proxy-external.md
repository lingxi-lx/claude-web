# 网络代理 / 外部写入的对话 / Codex 读取（2026-09-30 用户报告）

- **网络代理**（`server/src/net/proxy.ts`）：梯子在规则 / PAC 模式下只设系统代理，浏览器跟着走，Node 从来不看（fetch / node:http 都不认，`HTTP(S)_PROXY` 也只在启动前设了 `NODE_USE_ENV_PROXY` 才算），所以本服务自己的请求（供应商测试、拉模型、额度、IM、缓存垫片、模型网关）和它起的每个 CLI 以前都是直连——用户开着梯子测试连接得到 403「Access from this region requires trusted account access」。设置 `network.proxy`（meta.json，设置 → 供应商 → 网络代理，`settings/ProxySection.tsx`）：不存 = 跟随系统（先看启动时的 `HTTP(S)_PROXY`，再看系统代理：Windows `reg query HKCU\…\Internet Settings` 的 `ProxyEnable/ProxyServer/ProxyOverride`，或 `AutoConfigURL` 指向的 PAC 里第一个 `PROXY h:p`（不执行脚本）；macOS `scutil --proxy`；Linux 只认环境变量），**系统代理连不上就不用**（梯子崩了会把设置留下，TCP 探一下，状态里说明）；`'off'` = 全部直连（连环境变量里的也从子进程去掉）；http(s) 地址 = 用它（连不上也用，状态里提示）。SOCKS 地址 `settings.set` 直接拒绝（undici / https-proxy-agent 都不支持；让用户填梯子的 HTTP / 混合端口）。三处生效：① `process.env`：子进程（ccb、官方二进制、Codex、Gemini、终端、git）继承 `HTTP(S)_PROXY` + `NO_PROXY`（回环、局域网、Tailscale 的 100.64/10、`.local`、ProxyOverride；环境变量来源时代理原样保留、只补 NO_PROXY）——**以启动时的环境为基线**，每次重新决定都从基线算，不会越改越乱；② 本进程的 fetch：npm `undici` 的 `setGlobalDispatcher`（和 Node 22 / Electron 44 自带 fetch 共用同一个全局符号，两边都实测过），自写的按来源路由的 dispatcher（`bypasses()`：回环 / 局域网 IP / NO_PROXY 的主机、后缀、CIDR、端口）；一次都没需要过代理就不装，保持 Node 自己的；③ node:http / ws：`proxyAgentFor(url)`（`https-proxy-agent`，CONNECT 隧道，http 目标也走隧道，**请求字节不变**——网关透传的指纹不受影响），`gateway/upstream.ts`、钉钉 / Discord / Slack 的 ws、飞书 SDK（`defaultHttpInstance.defaults.proxy=false` + `httpsAgent`：axios 自己读 `HTTPS_PROXY` 时把 https 以明文绝对 URL 发给代理，多数梯子不收；`Lark.Domain.*` 是枚举数字，不是 URL）。**不轮询**：`proxy.refresh()` 距上次看超过 1 分钟才重看（Windows 一个 `reg` 进程），hub 里 `GOES_OUT` 表列的请求（session.open / send / setProvider / switchAgent、providers.probe / refreshModels、terminal.open、im.set / test、mcp.registry）先 await 它，`RunnerPool.open`（IM / 定时任务 / 目标直接走这里）、`ImService.start`、额度拉取也会刷新。`network.proxy {refresh}` 请求返回 `ProxyStatus`（密码打码）。已经在跑的对话要重开才用新代理（env 在 spawn 时定）。前端 `quick.ts` 的 `REGION_RE` / `REGION_BLOCKED`：地区拦截的错误（region / country / territory / location is not supported）不再说「Key 不对」，指到这个设置；供应商表单的测试结果下同样一行。phase19 带的死代理 `HTTP(S)_PROXY=127.0.0.1:9` 现在会被本进程用于非本机地址（它的检查都是 127.0.0.1，照样通过）。
- **CLI / Codex 在外面写的对话要实时显示**（用户报告：在终端里的 Claude CLI、或在 Codex 里发起的一轮，本应用里打开的那个对话不更新，一轮的收尾汇报也看不到，只有重启才补上）：服务端 `transcripts.changed {sessionIds}`——Claude 的 `SessionService` 监听器（`transcriptIdOf(rel)`：项目下的 `<id>.jsonl`）和对话库对 Codex 的监听（`codexRolloutId(rel)`：`sessions/…/rollout-<ts>-<uuid>.jsonl` → `codex-<uuid>`），都按 800 ms 静默合并一次。前端 `store/external.ts`：只有**不在本机跑**的已打开对话（state 是 history / closed / error）才重读——在跑的有自己的事件流；看得见的（每个窗格前面的标签）按 `nextReadAt()` 节流（至少 2 s，且读取耗时 ×4，60 MB 的 transcript 一秒一读也只占四分之一），看不见的记 `staleHistory`，切过去（`ChatTile` 的 effect）再读；重读后 `applyTranscript(…, {live: externalLive()})`：外部写入后 20 s 内最后一轮当作还在跑（工具不打勾、不折叠），过了再刷一次。导入的对话走 `library.read`，Claude 的走 `transcript.load`。
- **Codex 读历史**（`library/codex-source.ts`）：「thread not loaded: <id>」= Codex 里没有这个线程的历史（在 Codex 里删了，或者刚建、还没存第一条消息——都实测复现过；不是版本不一致）。`thread/turns/list` 第一页报这个 / `-32601` / 「requires experimentalApi」（0.130 以前）时退回 `thread/read {includeTurns:true}`；还是读不到就抛 `THREAD_GONE`（「Codex 里读不到这个对话：它可能已经在 Codex 里删除了…」），对话库清缓存重列并 `changed`，这个线程 10 分钟内不再列出（`GONE_HIDE_MS`）。`thread/list` 里 `path`（rollout 文件）已经不存在的线程不列（用户报告：删掉的对话也被识别出来）。mock：`MOCK_CODEX_DELETED=1`（一个 path 不存在、读了报 not loaded 的线程）、`MOCK_CODEX_OLD=1`（turns/list 要 experimentalApi）。
- **OpenAI / Gemini / Grok 格式的供应商忽略「只认官方二进制」**（用户报告：新建的工作区里 gpt 模型全是灰的）：官方二进制只会 Anthropic 协议，这三种类型只能在 ccb 上跑，所以 `@catalog` 的 `preferredRuntime(p)` 对它们一律返回 `ccb`（`session-runner` 选引擎、`providers.fitError`、前端 `effectiveRuntime` 都用它）；以前 probe 自动切到 `runtime:'claude'` 或手动勾过的旧档案，整张模型表都显示「官方 Claude Code 只支持 Anthropic 兼容…」。供应商表单只对 anthropic / gateway 显示那个勾选，保存其它类型时把 `runtime` 清掉。

- **Codex 里还在跑的一轮**（2026-10-14 用户报告：Codex 桌面版还在「正在思考」，这边已经是一轮的结尾「0s · 3 步 · 费用未知」）：`codexTurnsToMessages` 以前每个 turn 都 `endTurn`。现在最新一页的最后一轮在跑时（turn `status:'inProgress'`，或 rollout 尾部 256 KB 里最后一个 `task_started` 之后没有 `task_complete` / `turn_aborted`、文件 30 分钟内写过——`rolloutTurnOpen()`；路径来自 `thread/read {includeTurns:false}` 的 `thread.path`）不发 result、`inProgress` 的工具不发结果，读的结尾是一条 `{type:'system', subtype:'cw_elsewhere', agent:'codex'}`。前端 reducer 记成 `conv.elsewhere`（之后任何消息清掉它），`applyTranscript` 当 live 处理；ChatView 对 `readsFromOutside` 的对话显示「这一轮还在 Codex 里进行」。**镜像同步**（这里开的 Codex 对话）：`splitInFlight()` 把在跑的那一轮从提示词起切掉，不写进镜像——提示词是下一次同步的锚点，半轮写进去后半轮就永远补不上；`read()` 把它临时接在后面显示。真 Codex 验证不了（实测时账号额度用完）：app-server 的 turn 状态来自 `thread_history_1.sqlite` 的投影（写 rollout 的进程维护），所以另外看 rollout。

- **「正在别处更新」误报**（2026-10-14 朋友截图：一个对话下面突然出现，其它对话没有）：以前 `transcripts.changed` 一来就 `externalAt = now`，而我们自己的进程退出时（闲置回收、关掉）CLI 会往记录里写几行记账（last-prompt、cost-state、标题），监视器晚一点报出来时窗口的状态已经是 closed —— 于是显示 20 秒「别处在写」。现在 `externalChanged` 只安排重读，`refreshExternal` 读完比较「消息条数 + 最后一条 uuid」（`extSeen`），真的多了才算外面在写。基线：`loadHistory` 记一次；**本窗口自己的进程停下**（store 末尾的 `useStore.subscribe`：任何一个打开的对话从在跑变成 history / closed / error——`session.state` 事件、断线重连后 `session.info` 找不到进程直接标 history、发送没被接住标 error 都算；`bump()` 是原地改的，上一个快照里已经是新状态，所以自己记 `lastState`）时 `rebaseExt()` 再读一次——这时磁盘上的都是这里跑的，不重记的话「这个窗口里新开的对话」（从没读过盘）和「读进来后又在这里跑了几轮」的对话一退出照样误报（验证子代理用真 store 复现过，`store/external-seen.test.ts`）；重读和记账写入撞车时，先到的那次读就当基线（`extRebase`）。没有基线的读也只当基线，不报。
