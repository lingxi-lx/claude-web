# 供应商：IM / 定时任务 / 其它 Agent（2026-09-30 用户报告）

- **供应商在对话池里定**（`RunnerPool.open` 的 `resolveProvider()`）：调用方没给 `providerId` 时——IM、定时任务、目标、交接、编排都直接 `pool.open`，不经过 hub 的 `session.open`——恢复用记录的（`SessionMeta.providerId`，这个 agent 用得了才算），新对话用这个 agent 的默认：Claude = 设置 → 供应商的「设为默认」（`settings.defaultProviderId`），其它 agent = 设置 → Agents 与子代理卡片上的「新对话用」（`AgentConfig.providerId`，`agents.set`）。记录的供应商新 agent 用不了（从 Claude 交给 Codex）→ 那个 agent 的默认；恢复时什么都没记 → 账号 / agent 自己的登录（和以前一样）。池自己选的会写回 `SessionMeta.providerId`。显式给的（含 `'claude'` = 账号）永远优先，由调用方记录。以前钉钉机器人发的消息永远走 Claude 账号（用户报告）。`defaultProviderFor(agent)` 对外开放：`swapAgentNow` 显式传它（否则池会沿用旧 agent 记录的、新 agent 碰巧也收的那个），并记下来。
- **IM**：`ImGatewayConfig.providerId`（'' = 跟新对话一样，`'claude'` = 账号 / agent 自己的登录，其它 = 供应商；`ImService.set` 的字段表里要列出新字段），设置 → IM 机器人卡片上「用哪个供应商」；选的供应商这个 agent 用不了（后来改了 agent）→ 退回默认（`pool.providerFitError`）。`ImBinding.agent` 记下对话的 agent：以前闲置回收后重开 / `/use` 一个 Codex 对话会用 Claude 起在那个 id 上。`/new`、`/status` 的回复写「· 供应商 X」。
- **Codex 走供应商**：openai 型档案的 Codex 对话经缓存垫片（`agentLaunch(id, 'codex', kind, sessionId)` → `shimBaseUrl(p.shim, sessionId)` + 垫片密钥进 `CW_GATEWAY_KEY`，`codexProviderArgs` 的 base_url 指向垫片；`cacheShim:false` 退回直连）。垫片新开 `POST /v1/responses`（只对 openai 型）：先原样转发（Codex 没带 `prompt_cache_key` 才插），**「没有这个接口」**（404 / 405 / 501 且不是模型错误，和 `noResponsesApi` 同一个判据）就把这一次转成 chat/completions（`R.parseRequest` → `C.renderRequest`，回程 `C.ChatStreamParser` → `R.ResponsesStreamRenderer`；reasoning 项丢掉、`apply_patch` 这种 custom 工具变成只有 `input` 的函数、回程再变回 `custom_tool_call`；o 系列 / gpt-5 带上 `reasoning_effort`），chat 通了才记 `noResponsesApi`，之后直接转换。国内中转 / 厂商大多只有 chat/completions，以前 Codex 接上就是 404。账本行 `gateway.inbound: 'responses'`。池给用供应商的外部 agent 新对话**预先分配 id**（垫片路由和账本要用；驱动只在 transcript 头里有原生线程 id 时才恢复，所以仍是新对话），并在网关 / 垫片是本机地址时补 `NO_PROXY`（Codex 认 `HTTPS_PROXY`）。其它 ACP agent 选 openai 型供应商只拿到 `OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL`，用不用看它自己（卡片上写明）。
- **模型菜单**：`AgentSource.provider`：设了「新对话用」的 agent，它那一节列供应商的模型（标题「Codex · 中转名」，条目 `providerId` = 那个供应商），欢迎页选它 = 换 agent + 那个供应商；Claude 那一节用新对话默认供应商。组件 `features/providers/ProviderSelect.tsx`（Agents 卡片和 IM 卡片共用；列这个 agent 用得了的类型，末项「添加供应商…」走快速连接，加的是 Claude 格式、这个 agent 用不了时 toast）。
- **钉钉接口可以指到假服务**：`CW_DINGTALK_API`（默认 `https://api.dingtalk.com`），只给端到端检查用。
- `server/ws-phase19.mjs`（`npm run e2e` 默认列表里；**自己起 server**：要带死代理 `HTTP(S)_PROXY=127.0.0.1:9` 和 `CW_DINGTALK_API`）：真 ccb + 只有 chat/completions 的假中转 + 假钉钉（Stream 网关 http + ws，sessionWebhook 收回复）+ mock Codex（`codex-server.mjs` 带 `-c model_provider="cwgw"` 启动时像真 Codex 一样 POST `<base_url>/responses`，提示词含 `relay` 才问）：钉钉消息走默认供应商且 `/status` 写出来、重开保留、机器人选另一个供应商、Codex 机器人经垫片到只有 chat 的中转并记住、定时任务走默认、选的模型就是发出去的模型、中转不回时停止 0.2 s 结束、终端是 shell——全程系统代理是死的。真 Codex（0.158 原生 codex.exe，临时 `CODEX_HOME`）另外手工跑过：只有 chat 的中转、有 Responses 的中转（原样转发）、死代理下都能回答。注意本机 npm 装的 `codex.js` 被本地改过，会 require `<CODEX_HOME>/cli-app-sync/launch.cjs`，临时 `CODEX_HOME` 下起不来（`--version` 就挂）——测真 Codex 时直接指向 `@openai/codex-win32-x64/vendor/.../codex.exe`。
