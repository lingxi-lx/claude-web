# 思考强度 / 深度编排 / 自动判断在所有模型上（2026-10-08）

spec：`docs/superpowers/specs/2026-10-08-own-engine-uniform-capabilities-design.md`。翻译都在引擎里做（fork 的 `CLAUDE-WEB.md` 有文件表），claude-web 只告诉引擎每个模型能做什么、收下被拒的记录。

- **每个供应商、每个模型都有「智能程度」和「深度编排」**：能发原生参数的发参数，不能的走提示词（每轮跟着用户消息附一条 system-reminder「Reasoning depth: …」——一轮里的工具调用之后不再附；不压输出长度）。每种接口发什么在 fork 的 `src/services/api/effortPlan.ts`：Claude（含 Fable）`output_config.effort` + 4.6 起 `thinking:{type:'adaptive'}`（更早的发预算）；Claude 格式端点上会推理的别家模型（DeepSeek `/anthropic` 之类）发思考预算；OpenAI chat `reasoning_effort`（DeepSeek 一类同时 `thinking:{type:'enabled'}`）；Responses `reasoning.effort`；Gemini 3 `thinkingLevel`、2.5 `thinkingBudget`；Grok（grok-3-mini）`reasoning_effort`。
- **档位**：low < medium < high < xhigh < max；模型档位不全时就近，距离相同往高的靠（DeepSeek `{low,high,max}`：medium → high、xhigh → max）。来源：供应商 `/v1/models` 里每个模型的 `effort.supported_levels` / `default_level`（官方 DeepSeek 有；`parseModelList` 记进 `Provider.modelEfforts`）> catalog 的 `tableCaps()` > 全部五档。Claude 用 catalog 的逐模型档位（Opus / Sonnet 4.6、Sonnet 4.5 没有 xhigh），catalog 里没有的按版本（4.6 没有 xhigh，深度编排的 xhigh 就近到 max）。
- **告诉引擎**：runner 给供应商对话的引擎进程设 `CLAUDE_WEB_MODEL_CAPS`（`models/catalog.ts` 的 `webCapsEnv()`）：列表或表认识的每个模型都写 `modelCaps()` 的结论——这个格式能原生发的写 `{levels, default?, reasoning:true}`，其它的写 `{native:false}`（走提示词，也不带 DeepSeek 式思考开关）：别的格式的模型（OpenAI 格式中转上的 Gemini、网关后面的非 Claude 模型——网关转换时丢掉参数）、记下只能提示词的；两边都不认识的不写（引擎自己的名字规则和表覆盖同一批名字）。坏 JSON 引擎当作没有。2026-10-09 终审抓到以前跨格式时两边各算各的（界面写「通过提示词」，引擎却发了原生参数；网关上的 gpt-5 强度完全没作用）。账号的模型表是别名（default / opus / sonnet…），`modelCaps(undefined, 别名)` 先按 catalog 的 `aliases` 换成真模型；官方二进制上账号的条目照 CLI 自己报的档位（它没有提示词方式）。OpenAI 格式供应商上名字带 haiku / sonnet / opus 的 id，引擎的 `resolveOpenAIModel` 以前一律换成这个供应商的家族映射或默认模型（一个用 OpenAI 格式提供 `claude-sonnet-5` 的中转，选了它发出去的是默认模型）：cw.2 起 `providerEnv()` 把模型列表里这类 id 放进 `CLAUDE_WEB_SERVED_MODELS`（JSON 列表），列表里有的引擎原样发，没有的（引擎自己后台用的 Claude id）照旧按家族映射；phase 22 有一条。

- **所有模型都发原生强度**（2026-10-26 用户要求「确保所有模型都要带 reasoning effort」）：`modelCaps` 在 OpenAI 格式、Claude 格式、账号、网关四种档案上对**每个**模型 `native:true`（记在 `promptEffortModels` 里的除外），`webCapsEnv` 也给这四种档案的每个模型写 `{levels, reasoning:true}`——引擎只对 caps 标了 reasoning 的发参数。没人描述的 OpenAI 格式模型用标准三档 `low/medium/high`（以前是五档走提示词）。代价：OpenAI 格式上 `reasoning:true` 同时打开 DeepSeek 式思考开关（`thinking` / `enable_thinking` / `chat_template_kwargs`），不认的上游（官方 gpt-4o）第一次 400，引擎去掉开关重发并在这个进程里记住；不认 `reasoning_effort` 的照下一条退回并写进 `promptEffortModels`。Gemini / Grok 档案照旧按名字（引擎这两种目标只看名字，别的型号本来就不收这个参数）。**官方二进制**没有提示词方式、只给它自己认识的模型发：`session-runner.ts` 的 `modelEntry` 和 `web/.../intelligence.ts` 在 runtime 'claude' 上用 `native && reasoning`（＝以前 Claude 格式的规则）。
  **网关以前把请求里的强度整个丢掉**（`ir.ts` 开头那句「Thinking … dropped on purpose」原意是签名），网关后面的非 Claude 模型（「默认」里的 cn:deepseek-v4.1-flash 之类）从来收不到。现在 `IrRequest.effort`：Claude 的 `output_config.effort` / 思考预算（按引擎的预算表反推档位）、`reasoning_effort`、Responses `reasoning.effort`、Gemini `thinkingConfig` 都解析进来；`service.ts` 只在成员模型 `modelCaps(成员, 模型).native` 时保留，并 `nearestLevel` 到它的档位；写出：OpenAI chat `reasoning_effort`、Gemini 3 `thinkingLevel` / 2.5 `thinkingBudget`、Claude 4.6+ 只写 `output_config.effort`（**不开 thinking**：转换来的历史没有签名的 thinking 块，Claude 会拒「前面的 tool_use 没有 thinking」）。成员回 400 / 422 且错误点名强度参数（`cache.ts` 的 `mentionsEffort`）→ 不带参数重发一次，`effortRefused`（成员 id + 模型，进程内）记住，客户端看不到失败。缓存垫片的 Codex → chat 回退同样按成员 caps 发，不带参数的重发体兜底。测试：`convert.test.ts` 的 thinking strength、`service.test.ts` 的拒收重发、`shim.test.ts`、`catalog.test.ts`、`session-runner.test.ts`、web `intelligence.test.ts`。
- **参数被拒**：HTTP 400 / 422 → 引擎去掉参数重发一次（这一轮照样答出来）；错误文本点名**这个目标发的**参数（`effortRejection.ts` 的 `TARGET_PARAMS`：Claude 只认 `output_config` / `effort`、预算认 `thinking`、OpenAI 认 `reasoning_effort`…；说 thinking 块 / 签名 / 某个值不对的都不算）才记住：引擎发 SDK 消息 `{type:'system', subtype:'cw_capability', model, capability:'native_effort', supported:false, …}`，runner 收下（不转给窗口）、pool 写进供应商的 `promptEffortModels`，以后这个模型走提示词。供应商编辑里「保存后重新检测」清掉这张表。没点名的不记，但同一进程里同一模型被这样拒两次，这个进程就不再发这个参数（只在进程里，不报、不写供应商）——否则一轮里每一步都先失败一次（经缓存垫片是 3 个上游请求）。
- **界面**：会话 info 的模型带 `effortMode: 'native' | 'prompt'`；提示词方式时菜单说明一句（`terms.ts` 的 `EFFORT_MODE_NOTE` / `EFFORT_PROMPT_TITLE`）。欢迎页、运行中、没在跑的对话都用 `features/models/intelligence.ts` 的 `claudeEffortView()`。
- **深度编排**：引擎的 `--ultracode` / `ultracode` 设置，所有模型都可用：开着时每轮一条「Ultracode is on for this session…」，打开后的第一轮附编排说明（`/ultracode` 的 playbook），强度按 xhigh。2026-10-09 真 DeepSeek 实测会调 Workflow 工具。开对话时就选了（欢迎页、重开）：我们的引擎带 `--ultracode` 启动；官方二进制在第一条消息之前补发 `/effort ultracode`（开对话时就发会凭空生成一个以这条命令为标题的对话）。欢迎页 / 没在跑的对话上选档位会同时关掉深度编排（`store/reopen.ts` 的 `mergeResume()`，和运行中的 `setEffort` 同一条规则）。
- **自动判断**（`permissionMode:'auto'`）：判断请求是强制调用 `classify_result` 的工具调用；默认会思考的模型（DeepSeek、MiMo、caps 说会推理的）一开始就关思考发（DeepSeek 不收「思考 + 强制工具」），被拒逐级退回（关思考 → `tool_choice:'auto'` → 去掉思考开关并记住），暂时性错误重试一次（fork 的 `src/utils/sideQueryRetry.ts`）。
