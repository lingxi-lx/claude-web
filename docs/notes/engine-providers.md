# 引擎（单运行时）与供应商档案

- **只有一个运行时**：`server/src/claude-exe.ts` 的 `resolveEngine()` 优先我们自己的引擎（包 `claude-web-engine` 的 `dist/cli-node.js`，根 package.json 的依赖是本仓库一个 Release 上的 tgz 地址，见下一条；代码里的运行时名字仍叫 `ccb`），找不到时静默退回 SDK 自带的官方 claude.exe。不再找全局安装的 `claude-code-best`，配置中心也没有「更新 ccb」按钮了（引擎跟着 claude-web 一起发版）。`engineInfo()` 给配置中心显示版本。`CLAUDE_WEB_RUNTIME=claude` 或档案的 `runtime:'claude'` 可强制官方二进制。ccb 是 JS，SDK 用 `node` 起它；Electron 里没有 `node`，`spawnClaude` 映射成 `process.execPath` + `ELECTRON_RUN_AS_NODE=1`。
- **ccb 的模型别名比官方旧**（2026-09-29 用两个引擎的 `system/init` 实测，`--model <别名>`）：官方 Claude Code 2.1.283（Max 账号）默认 → `claude-opus-5-5[1m]`、opus → `claude-opus-5-5`、sonnet → `claude-sonnet-5`、haiku → `claude-haiku-4-5-20251001`、fable / best → `claude-fable-5-1`；ccb 2.8.4 默认 / opus → `claude-opus-4-7`、sonnet → `claude-sonnet-4-6`、best → opus-4-7、`fable` 原样发出去（API 不认）。所以**账号登录 + ccb** 的对话由 runner 注入 CLI 自己认的 `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`（`models/catalog.ts` 的 `OFFICIAL_ALIAS_TARGETS` / `ccbAccountEnv()`；ccb 的默认模型跟着 opus 那个走，实测和官方逐个一致），`fable` / `best`（含 `[1m]`）由 `ccbModel()` 改写成 `claude-fable-5-1`；进程 env 或 `~/.claude/settings.json` 里用户自己设了这些变量就不动，供应商档案的对话走档案自己的映射。catalog 的 `aliases` 同一张表，芯片上的名字就是真正在跑的模型（以前 opus 显示「Opus 5」实际跑 4.7）。**升级 SDK 自带的 claude 二进制后要重新量一遍**（`--model <别名>` 起一次、读 init 行的 `model`）。
- **引擎 = ccb 2.8.4 的 fork**（2026-10-08）：仓库 `https://github.com/ypyik0669/claude-code.git` 的 `claude-web` 分支（`main` 是上游，不动），本机克隆在 `C:\Users\YPY\claude-web-engine`；改了什么写在那个仓库的 `CLAUDE-WEB.md`。版本号 `2.8.4-cw.N`。
  - **发布 = 本仓库的一个预发布 Release**（2026-10-09 用户决定，不发 npm：发布要 npm 账号；fork 是私有的，它的 Release 别人下载不了）：fork 里构建打包后，`gh release create engine-v<版本> claude-web-engine-<版本>.tgz --repo ypyik0669/claude-web --target main --prerelease --latest=false`，根 package.json 的依赖写 `https://github.com/ypyik0669/claude-web/releases/download/engine-v<版本>/claude-web-engine-<版本>.tgz`，再 `npm install` 更新 lock。**必须是预发布**：桌面版的 electron-updater（`allowPrerelease = false`）和手机壳站点的部署都只看 GitHub 的 `releases/latest`，一个被标成「最新」的引擎 Release 会让所有桌面版找不到更新文件；`engine-` 开头的标签也不会触发本仓库的工作流（它们只认 `v*`）。**上传过的文件永远不替换**：lock 里的 integrity 锁着它的字节，换了内容别人的 `npm ci` 就校验失败——改内容就发新版本号。上传后不带登录 `curl -L` 下载一遍核对 sha512，并确认 `releases/latest` 还是应用的版本。
  - 本地联调：fork 里 `bun run build:vite` + `npm pack --ignore-scripts`，claude-web 里 `npm install "claude-web-engine@file:../claude-web-engine/claude-web-engine-<版本>.tgz"`（同名 tgz 换了内容时 `npm install` 不会重装，要这样显式装一次更新 lock 的 integrity；装的时候带 `CLAUDE_CODE_SKIP_CHROME_MCP_SETUP=1`，引擎的 postinstall 会注册 Chrome native host）。
  - **ccb 2.8.4 的「自动判断」没有判断提示词**，cw.1 修好了：node 构建里提示词是 Vite 的资源引用（`/assets/auto_mode_system_prompt-*.txt`），文件不在包里，安全判断请求的 system 就是这个路径。fork 的构建把 `.txt` 都内联，`scripts/check-inlined-text.ts` 在构建后检查。
  - **Windows 上构建的包以前有两份会话状态**（2026-10-09 phase 22 抓到）：`src/` 别名在 Windows 上解析成反斜杠路径，和相对导入不是同一个模块 id，同一批文件打了两份（654 个 chunk，上游 621），`--session-id` 改的是一份、读的是另一份——每个对话第一轮之后 id 就变了，后续请求「session … is not open」。fork 的别名改成正斜杠，`scripts/check-single-state.ts` 在构建后检查只有一份。
- ccb 是官方的超集：完整实现 stream-json + control 协议，只缺 `supported_commands` / `supported_models` / `commands_changed`（runner 从 `initializationResult()` 的 `commands`/`models` 兜底）；共用 `~/.claude`（登录、settings、会话 jsonl、subagents）。
- **供应商档案**（`Provider`，存 `~/.claude-web/meta.json`，不写 `~/.claude/settings.json`）：`server/src/providers/service.ts` 的 `providerEnv()` 按类型映射成 env（anthropic → `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`（Bearer）+ `ANTHROPIC_MODEL` / `ANTHROPIC_DEFAULT_*_MODEL`；openai → `OPENAI_BASE_URL` + `OPENAI_API_KEY` + `CLAUDE_CODE_USE_OPENAI=1`（base 补 `/v1`）；gemini → `CLAUDE_CODE_USE_GEMINI=1` + `GEMINI_API_KEY` + `GEMINI_BASE_URL`（补 `/v1beta`，ccb 请求 `<base>/models/<id>:streamGenerateContent`）+ 三个 `GEMINI_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL`（缺的用 defaultModel / 第一个模型补齐：ccb 的 Gemini 客户端遇到没映射的 haiku/sonnet/opus 直接抛错）；grok → `CLAUDE_CODE_USE_GROK=1` + `GROK_API_KEY` + `GROK_BASE_URL`（OpenAI SDK，补 `/v1`）+ `GROK_DEFAULT_*_MODEL`（缺的走 ccb 自带的 grok 默认）。**不设 `GEMINI_MODEL` / `GROK_MODEL` / `OPENAI_MODEL`**：ccb 对每个请求都返回它们，会让会话内换模型失效（`OPENAI_MODEL` 到 v0.1.0 还在设，openai 档案在菜单里选什么都发默认模型，haiku / sonnet / opus 映射也全被忽略——2026-09-30 用户报告后修掉；会话模型由 runner 的 `params.model || defaultModel` 给，`OPENAI_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL` + `OPENAI_SMALL_FAST_MODEL` 缺的用默认模型 / 第一个模型补齐，否则 ccb 退回它自带的 claude → gpt-4o / o3 表）；不带 haiku/sonnet/opus 字样的模型 id 原样透传。ccb 选提供方看 `getAPIProvider()`：settings 的 `modelType` 优先，其次 `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY/OPENAI/GEMINI/GROK`，都没有就是 Anthropic——没开关的 gemini / grok 档案会静默走 Anthropic 默认通道（踩过）；用户 `~/.claude/settings.json` 里写了 `modelType` 会压过这些开关。官方二进制没有这些通道，所以这三种类型只在 ccb 上可用（`profileFitError`）。），`session-runner.ts` 只注入到那个会话的进程；本进程的 `ANTHROPIC_*` / `OPENAI_*` / `GEMINI_*` / `GROK_*` / `XAI_*` / `CLAUDE_CODE_USE_*` env 会被清掉以免混入。会话用的档案记在 `SessionMeta.providerId`，resume / fork 沿用。wire 上 `apiKey` 一律打码。
- **中转指纹（api.super-nb.me 实测）**：只放行官方 Claude Code 构建发的 `/messages`。三处判据都踩过：① User-Agent 里不能有 SDK 附加的 `agent-sdk/x.y.z`（来自 env `CLAUDE_AGENT_SDK_VERSION`，`spawnClaude` 见到 `CLAUDE_WEB_PLAIN_UA` 就删掉）；② `CLAUDE_CODE_ENTRYPOINT` 必须是 CLI 默认的 `cli`（`sdk-ts`/`claude-web` 都 400「请求可能被第三方中转改写」）；③ 必须带 Claude Code 的主系统提示（Agent SDK 默认是**空**系统提示，runner 显式传 `systemPrompt: {type:'preset', preset:'claude_code'}`）。ccb 本身的请求形状（UA 2.8.4、不同的系统提示和工具表）过不了这种指纹，所以 `ProviderService.probe()` 除了 `/v1/models` 还真跑一轮 `-p`：ccb 被拒就自动把档案 `runtime` 切到 `claude` 并提示。
- **中转还卡最低 CLI 版本**（2026-09-27 实测 super-nb 要求 ≥ 2.1.280）：官方二进制来自 `@anthropic-ai/claude-agent-sdk-<平台>`，版本跟 SDK 走（SDK 0.3.x ↔ Claude Code 2.1.x），被拒时报「客户端版本过低」就升级 SDK。
- **用户 settings 文件里的 `env` 压过我们给 CLI 的 env**（2026-10-07 实测，官方二进制和 ccb 都是，经 SDK 也一样）：`~/.claude/settings.json`（以及项目的 `.claude/settings.json` / `settings.local.json`）的 `env` 会在启动后盖到进程环境上。cc-switch 之类的工具会往那里写 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL`，结果供应商对话拿旧 Key 发到我们的中转（401，CLI 默认重试 10 次、几分钟），或者整个发到旧中转去（「测试连接」也照样「通过」）；模型列表是我们自己用新 Key 拉的，所以看上去 Key 没问题。修法：供应商对话（`SessionRunner.start`）和 `chatProbe` 用 `runtime/user-env.ts` 的 `settingsOverride(ours, cwd)` 算出冲突——settings 文件里出现、我们也设了的键用我们的值，出现了而我们没设的路由键（`ROUTING_ENV`，和清进程 env 同一个正则）设成 `''`（CLI 当作没设：不发多余的 x-api-key、用自己的默认模型）——经 `--settings <文件>`（flag 层，优先于 user / project / local）传进去。**用文件不用内联 JSON**：SDK 的 `settings` 对象会原样放进命令行（`--settings {"env":…}`），macOS / Linux 上别的用户 `ps` 看得到 Key。文件 `runtime/flag-settings.ts` 写在 `<dataDir>/runtime/flag-settings/<server pid>-<uuid>.json`（0600，目录 0700），只在有冲突时才写，跟着那个 CLI 进程（`exit` / `error` 时删，`close()` 兜底没起来的），别的 server 已经不在的文件在第一次写时清掉。账号对话不动（用户自己在 settings.json 配的中转就是他要的）。没有冲突就什么都不写、不传。
- 注意本机开发 shell 继承了 `CLAUDE_CODE_ENTRYPOINT=sdk-cli`（因为在 Claude Code 里跑），测指纹要用 `env -u` 或显式赋值，别被继承值骗了。
- 会话级开关 `SessionFeatures`（`--chrome`、`--computer-use-mcp`、`--proactive`、`--brief`、`--channels`、`CLAUDE_CODE_COORDINATOR_MODE`）在 `session-runner.ts` 的 `featureArgs()/featureEnv()`。
- Langfuse / Artifacts / Web Search 等配置仍是 `~/.claude/settings.json` 的 `env`；设置 → 高级 → 环境变量编辑（`features/settings/EnvEditor.tsx`，停靠面板配置中心「供应商 / 环境」tab 下半段是同一个组件）。
- ccb 里 `local-jsx` 类型的命令（/goal 面板、/artifacts 列表、/poor、/voice、/buddy 等）是 TUI 专属，headless 发不了；对应能力靠工具（Goal / Artifact / Workflow）或终端面板兜底。
- **上下文窗口**（2026-10-14 用户报告：中转的 Claude 175K 就压缩；cw.4）：两个引擎都只认得自己表里的模型，其它一律 200K（`[1m]` 后缀 = 1M；ccb 的 GPT-5.6 表在 API Key 下是 1.05M）。`server/src/models/context-window.ts`：用户设的（`Provider.contextWindows`）> 模型列表写的（`modelContext`：`context_length` / `max_input_tokens` / `inputTokenLimit` / `context_window`…，随列表一起拉）> 按名字拉满（`knownContextWindow`：Claude 1M、Haiku 200K、GPT-5/6 272K、Gemini 2.5+ 1,048,576、Kimi / Qwen-coder / Grok-4 256K、DeepSeek 128K）> 引擎默认。**我们的引擎**：`CLAUDE_WEB_CONTEXT_WINDOWS`（JSON，模型 → token，fork 的 `getConfiguredContextWindow()` 排在最前；Claude 模型超过 200K 时同时带 1M beta 头），供应商所有模型一张表，对话中途换模型也对。**官方二进制**没有这种开关：`officialWindow()`——Claude 模型超过 200K 就以 `<model>[1m]` 启动 / setModel（runner 的 `engineModel()`；没选模型时用供应商默认模型加后缀），比它会假设的小就设 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`（只能往小调；按启动时的模型算，中途换模型不跟着变）。Codex：`-c model_context_window=<默认模型的窗口>`。设置页：编辑供应商里「上下文窗口」（ConfigPanel 的 `ContextWindows`，空着显示默认值和来源）。**实测**（super-nb，2026-10-14）：官方二进制 + claude-sonnet-5-5 → init 模型 `claude-sonnet-5-5[1m]`、`getContextUsage` 的 `raw_max_tokens` 1,000,000，回复正常；设成 400K → 400,000；OpenAI 格式副本 + gpt-5.6-sol 在 ccb 上 → 272,000（请求本身被这个 Key 的分组拒了，403 This group is restricted）。ccb + Claude + 1M beta 没验证到：这两个中转对 ccb 的 Claude 请求一律 400「请求可能被第三方中转改写」（发不发 beta 都一样，所以它们都钉在官方二进制上）。
- **换模型和上下文窗口**（2026-10-14 用户要求）：① 官方二进制的 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 是启动时读的，runner 的 `plan()` key 带上 `:compact-<n>`（`officialCompactWindow()`），换到需要另一个值的模型 = 另一个进程（`respawnWhenIdle`，resume 原对话）。**官方二进制给这个变量设了 100K 的下限**（设 50K 报 100K，120K 报 120K，phase 27 实测）。② `fitBeforeSwitch()`：`setModel` 先 `getContextUsage`，用量超过新模型窗口（`windowOf()`：供应商设置 / 引擎默认；账号上 `[1m]` 1M、其它 200K、`default` 不管）的 80%（`FIT_SHARE`）就发 `cw_notice`（reducer 的 `cw_notice` → 一行 info 系统消息，不进 transcript），再 `send('/compact')` 等这一轮的 result，然后才换。真中转（super-nb，官方二进制）：Sonnet 5.5 用到 402K → 换 Haiku（设成 100K）→ 提示、Sonnet 压缩 402K → 1.4K（16 s，$0.14）、换过去窗口 100K、Haiku 答对压缩前清单里的规律。③ **SDK 的 `getContextUsage` 回的是驼峰**（`totalTokens` / `rawMaxTokens`），`/context` 结果行才是下划线；以前前端只读下划线，上下文小环的悬停一直是 0 / 0——`conversation.ts` 的 `contextUsageOf()` 两种都认。
- **允许 = 必须带 updatedInput**（2026-10-14 社区用户报告：中转 + Claude 5.5 Sonnet，改文件 / 跑命令全失败，读文件正常，模型说「请求体里少了 updatedInput」）：claude-web-engine（ccb）`structuredIO` 用 `PermissionPromptToolResultSchema` 校验 SDK 的回答，`updatedInput` 是必填；我们的「允许一次」/ 手机 / IM / 总览只发 `{behavior:'allow'}`，校验失败被当成 `Tool permission request failed` 拒掉。官方二进制不要求，所以以前在官方二进制上没事。`respondPermission()` 统一补 `updatedInput: event.input`。e2e phase 27 两个引擎都测（默认权限模式下 Write，回一个光秃秃的 allow，文件要写出来）。
